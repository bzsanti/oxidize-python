# Release v0.5.2

## Summary

Patch release that pulls in upstream `oxidize-pdf` v2.8.2 — which fixes two text-rendering bugs reported against the 0.5.1 Python binding — and clarifies the `page_count` property documentation across `Document`, `PdfReader`, and `LazyDocument`.

## Bug Fixes

- **#57 — `set_fill_color()` did not paint subsequent text** *(upstream `oxidize-pdf` #239)*. After drawing a filled shape, a subsequent `page.set_fill_color(new_colour)` followed by `page.text_at(...)` left the text inheriting the prior fill colour because the writer did not emit a fresh non-stroking-colour (`rg`) operator inside the text object. Upstream now unifies the non-stroking-colour state across the graphics and text contexts so `set_fill_color` controls both shape fills and glyph fills, matching PDF spec semantics.
- **#58 — `text_flow_at()` ignored `set_default_font_encoding(WIN_ANSI)`** *(upstream `oxidize-pdf` #240)*. `text_flow_at` emitted the input string as raw UTF-8 bytes into the Contents stream, so every multi-byte glyph (€, em-dash, smart quotes, accented letters) rendered as 2-3 wrong characters under Helvetica/WinAnsi. Upstream now routes the text-flow code path through the same encoding pipeline as `text_at`, so both API surfaces produce identical bytes for the same input.
- **#59 — `help(Document.page_count)` documented a property as a method**. The three `page_count` getters (`Document`, `PdfReader`, `LazyDocument`) are read-only properties (`#[getter]`) — accessed as `obj.page_count`, never called as `obj.page_count()`. Without an explicit note in the docstring, `help()` rendered them as methods, leading users to invoke them and hit a confusing `TypeError: 'int' object is not callable`. Docstrings now state the property contract explicitly. No runtime behaviour change.

## Tests

Nine new regression tests parse the actual PDF Contents stream (via `PdfReader.get_page_content_streams(idx)`) and assert behaviour against the emitted operator bytes — not byte counts or `is_ok` checks:

- `tests/test_issue_57_text_fill_color.py` (4 tests) — verifies a white `r g b rg` operator (with `r=g=b=1`) is emitted both anywhere in the Contents stream and inside the `BT…ET` text block, that it appears after the magenta `rg` used for the rectangle fill, and that at least two distinct `rg` operators reach the stream.
- `tests/test_issue_58_textflow_winansi.py` (5 tests) — verifies `text_flow_at` emits the WIN_ANSI representation of `€` (raw byte `0x80` or PDF octal escape `\200`) and em-dash (`0x97` / `\227`), that the raw UTF-8 sequences for `€` (`E2 82 AC`) and `—` (`E2 80 94`) never leak into the stream, and that `text_at` and `text_flow_at` agree on encoding for the same input.
- `tests/test_document.py::test_page_count_is_read_only_property` — asserts `Document.page_count` is `int`, calling it raises `TypeError`, and `help()` no longer documents it as a method.

## Upstream

- **`oxidize-pdf` `=2.8.0` → `=2.8.2`.** Pinned exact equality preserved. Feature set unchanged (`compression, signatures, semantic`, `default-features = false`).

## Compatibility

- No API surface changes at the Python level.
- All public method/property signatures preserved.
- Wire-format change: PDFs generated by this release will contain the previously-missing `rg` operator before text after a fill colour change (#57 fix), and a WIN_ANSI-encoded operand inside `text_flow_at` literals (#58 fix). Both are PDF-spec-conformant; viewers that previously rendered text in the wrong colour or as garbled glyphs will now render correctly.
